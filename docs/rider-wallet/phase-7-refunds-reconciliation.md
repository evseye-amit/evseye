# Rider Wallet Phase 7: refunds, deposit returns, and settlement reports

## Implemented flows

Provider refunds reuse the Phase 4 `PaymentRefund` and `PaymentRefundService`. A client admin may now request a full or partial refund by passing an optional decimal `amount`. The payment row is locked during the refundable amount calculation. Successful and processing refund records reserve value. A database sequence generates a unique `EVR-YYYYMMDD-NNNNNN` refund number. A source refund ID and idempotency key are generated once and reused for provider retries. Provider responses are verified by the existing Cashfree adapter before `RiderPaymentsService` appends a refund ledger entry and updates the payment's refunded and unallocated totals. The original gross payment remains unchanged. New requests default to `UNALLOCATED_RETURN`, which requires unallocated money and never reopens an invoice. An explicit `PAYMENT_REVERSAL` treats a full original-payment refund as a reversal of its invoice allocations. Partial billing corrections need an explicit adjustment or allocation reversal first. Historical refund rows default to `PAYMENT_REVERSAL` to preserve their established meaning. Cashfree checkout and subscription refund create/fetch operations already existed in the payment provider interface. Signed refund webhooks now verify the raw body, record an idempotent provider event, and fetch the authoritative refund status before using the same finalization method as polling. An hourly job rechecks up to 100 pending refunds, including uncertain provider responses; failures are logged for the finance review queue.

Wallet security deposit return requests now select either `WALLET_CASH` or `MANUAL_OFFLINE`. Request creation reserves the amount with a hold. A different client admin must approve. Approval rechecks active allocation, rental agreement, outstanding invoices, and deposit availability. Wallet cash approval atomically releases the hold and posts `SECURITY_DEPOSIT_REFUND` from the deposit bucket to the cash bucket. Manual offline approval leaves the request in `PROCESSING`; after an externally executed transfer, an admin records its reference and the same ledger type debits the deposit bucket against clearing. Both paths are idempotent and audit logged. Rider security deposit detail and list responses include return request status, amount, destination, and dates without administrative actor data. This is an attested manual transfer, not an integrated bank payout. Existing deposit deduction operations use policy reason codes and immutable wallet ledger transactions. The separate rental-agreement `RiderDeposit` and `FinalSettlementService` already support settlement deposits and manual returns; they are not consolidated by this phase.

Cashfree settlement reports can be imported as normalized rows through `POST /client/finance/provider-settlements/imports`. The importer validates decimal totals (`gross - refunds - fee - tax = net`), item totals, unique references, and report identity. It matches each payment/refund item to a client-owned Cashfree collection, AutoPay transaction, or successful refund. Unknown, pending, and mismatched records are kept as review items; no rider allocation is guessed. Identical imports return the original immutable record; changed data under the same settlement ID is rejected. `GET /client/finance/provider-settlements` and `GET /client/finance/provider-settlements/:id` expose the imported report and review codes to client admins. These are operator supplied normalized report rows; the integration does not yet fetch Cashfree reports or attest bank arrival.

## APIs

- `POST /client/riders/:riderId/payments/:paymentId/refunds`: `Idempotency-Key`, `{ "reason": "...", "amount": "300.00", "treatment": "UNALLOCATED_RETURN" }`; omit `amount` to request all remaining refundable value. Use `PAYMENT_REVERSAL` only for a full original-payment reversal.
- `POST /client/riders/:riderId/payments/refunds/:refundId/verify`, `GET /client/riders/:riderId/payments/refunds`, and `GET /rider-app/payments/refunds` continue to provide status and history. Cashfree callbacks use `POST /webhooks/payments/cashfree/refund` for checkout and `POST /webhooks/payments/cashfree/subscription-refund` for subscriptions.
- `POST /wallets/security-deposits/:id/refund-requests`: `Idempotency-Key`, `{ "amount": "2200.00", "reason": "...", "destinationType": "WALLET_CASH" }` or `MANUAL_OFFLINE`.
- `POST /wallets/security-deposits/:id/refund-requests/:requestId/approve` and `POST /wallets/security-deposits/:id/refund-requests/:requestId/complete-manual` (body `{ "externalReference": "..." }`).
- `GET /rider-app/wallet/withdrawal-eligibility` reports cash available and the disabled external withdrawal rail; it never offers promotional rewards or security deposits as cash withdrawals.
- `POST /client/finance/provider-settlements/imports` accepts `providerSettlementId`, `currency`, `grossAmount`, `refundAmount`, `feeAmount`, `taxAmount`, `netAmount`, `settledAt`, optional `utr`, and payment/refund `items` with `kind`, `providerReference`, and `amount`.

All admin routes use the existing access token, client context, and `CLIENT_ADMIN` role. Rider refund history remains scoped to the authenticated rider. Amounts are decimal strings in requests. Migrations `20260927180000_partial_payment_refunds`, `20260927181000_provider_settlement_reconciliation`, `20260927182000_unique_deposit_return_reference`, , `20260927183000_refund_allocation_treatment`, and `20260927184000_refund_number` add multi-refund support, deposit return states, unique manual return references, refund treatment, and durable settlement review records.

## Accounting and remaining work

The rider payment ledger receives a new reversal entry after verified provider refund success. Deposit returns use new balanced wallet entries, preserving original funding. The imported settlement is a statement and reconciliation record, **not** a bank ledger posting: the current wallet accounts are rider scoped and cannot safely represent one bank settlement containing payments for many riders. A client level bank/fee/tax accounting destination and verified bank settlement feed are needed before automatic settlement posting. The same gap prevents claiming bank/UTR reconciliation from a manually entered report.

This implementation does not add a Cashfree settlement fetch endpoint, an external payout provider, deposit deduction approval records, an arbitrary wallet cash withdrawal rail, or general finance adjustments. Existing polling verifies refunds through the provider. Existing final settlement services cover agreement-level notes and manual refunds, and Phase 6 reward credits remain non-withdrawable. Review queue items are exposed for finance action without automatic corrections. Phase 8 must not infer that a matched provider report means cash reached the bank.
