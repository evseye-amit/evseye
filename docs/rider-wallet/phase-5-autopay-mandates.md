# Rider Wallet Phase 5: AutoPay mandates and collection

## Architecture

Phase 5 extends the existing `PaymentMandate`, `PaymentTransaction`, `PaymentAttempt`, `PaymentProviderEvent`, collection policy, and Cashfree subscription adapter. It does not create a second payment accounting path. A recurring charge is a `PaymentTransaction` (AutoDebit equivalent) with a human-readable `debitNumber`; each has a `PaymentAttempt`. Verified provider success calls `RiderPaymentsService.confirmProviderPaymentInTransaction`, then posts the same wallet clearing/provider-clearing double entry used for external checkout payments. The transaction, receipt, invoice allocation, wallet ledger, and dunning resolution commit together.

Riders explicitly enroll through the existing `/rider-app/payments/autopay` mandate route with an Idempotency-Key and `method` of `UPI_AUTOPAY` or `ENACH`. Client package configuration determines amount, validity, and allowed methods. Cashfree returns a subscription checkout session. Neither a mobile callback nor the create response activates a mandate; status is refreshed from Cashfree after authorization or a signed webhook. The provider adapter uses Cashfree Subscriptions API version configured by `CASHFREE_API_VERSION` (default `2025-01-01`) and an on-demand plan. It sends `upi` or `enach` in `authorization_details.payment_methods`. The customer completes authorization on the provider's hosted flow; EVsEye stores no PIN or bank credentials.

Mandate provider status is separate from EVsEye's `autoDebitEnabled` switch. Local disable prevents new debits but does not cancel a provider mandate or erase a payment already pending. Mandates have a unique `EVM-...` reference; debit transactions have a unique `EVD-...` reference. UUID-derived suffixes avoid `count(*) + 1` races. Historical mandates and debits remain stored. An hourly job expires locally overdue mandates and records an event and audit. Cashfree PAUSE, ACTIVATE, and CANCEL are exposed as rider actions; the result passes through the same state transition handler as polling and webhooks. Terminal statuses and ACTIVE are protected from stale backward updates.

## Collection

The client collection policy defaults to rental invoices only, with deposit, onboarding, penalty, and other categories requiring explicit opt-in. `walletFirst` defaults to true. Each hourly scan checks policy, invoice category, local switch, active and valid mandate, pending payments, retries, provider schedule horizon, mandate limit, and client maximum. It settles eligible reward/cash wallet funds under wallet and invoice locks using the Phase 3 funding planner, re-reads outstanding, and creates a provider charge only for the remaining amount. Full wallet coverage creates no provider debit. The orchestrator rechecks the invoice in a serializable transaction and again before calling Cashfree. A stable `autopay:<invoice>:<attempt>` key, active-collection check, and database uniqueness protect repeated scheduler runs. The provider charge is scheduled in the future for Cashfree's pre-debit process. `preDebitNotifiedAt` records its signed notification event; it is not evidence of payment.

A failed verified charge leaves the invoice outstanding and opens or updates `AutoPayDunningCase`. Only explicitly retryable failures are retried, within configured attempt count and interval. Every retry uses current invoice outstanding, so a manual payment reduces or eliminates the next charge. Nonretryable failures and amount/mandate limits require rider action. The hourly reconciliation resolves dunning once the invoice is paid or voided, including payment by manual checkout. `graceUntil` is recorded from the rider profile; Phase 5 does not immobilize vehicles or impose penalties. Cashfree may perform its own network retries inside one scheduled charge; EVsEye retries create a new logical transaction only after the previous one has a verified terminal failure.

## APIs

Rider routes under `/rider-app/payments/autopay`: GET current, POST create mandate, POST `:mandateId/verify`, POST `:mandateId/pause`, POST `:mandateId/resume`, POST `:mandateId/cancel`, POST `disable`, POST `enable`, GET `upcoming`, GET `debits`. Provider actions require Idempotency-Key. Rider identity always comes from the access token. Upcoming entries show scheduled and current outstanding amounts separately because wallet use or manual payments can change the eventual remaining amount.

Client admin routes under `/client/autopay`: GET `riders/:riderId`, `mandates`, `debits`, and `dunning`. Every query is scoped to the authenticated client. The existing `/client/payment-collection-policy` manages category, retry, maximum, and wallet-first settings. The existing signed `/webhooks/payments/cashfree` route stores provider event hashes for idempotency, fetches authoritative mandate/payment status, and routes successful charges through the one confirmation pipeline.

## Provider and deployment notes

Cashfree Subscriptions supports UPI AutoPay and eNACH, on-demand charges, status fetch, and subscription management. Cashfree documents merchant-initiated charges and pre-debit notifications; the scheduler requests at least 24 hours before the debit date and uses a future India calendar date. Confirm timing and eligible merchant category for the live Cashfree account before production enablement. Provider-specific amount and frequency limits can depend on rail, category, and account enablement; the package mandate maximum and client maximum provide server-side caps. The Cashfree adapter validates INR and schedule date. A dedicated EVsEye notification sender is not implemented; Cashfree handles provider pre-debit notice, while the signed notification event is recorded for audit.

Use `PAYMENT_PROVIDER=mock` for local tests. For Cashfree sandbox, configure API credentials, subscription return URL, webhook secret, and `CASHFREE_API_VERSION`; register the signed subscription webhook URL. Test UPI and eNACH authorization, cancellation, successful/failed charge, notification, duplicate webhook, and status polling against an enabled Cashfree sandbox account. Automated tests use mocks; no live Cashfree sandbox transaction was executed in this phase.

Migration `20260927150000_autopay_lifecycle` adds mandate/debit references, local switch, wallet-first policy, and dunning. Migration `20260927151000_autopay_predebit` adds the notification timestamp. The design leaves the Phase 2 REWARD bucket available for Phase 6 rewards without generating rewards in Phase 5.

A charge already accepted and scheduled by Cashfree remains independently trackable if the rider later disables or cancels the mandate or pays manually. EVsEye does not claim that the provider cancels an in-flight scheduled charge. If Cashfree later confirms it after the invoice was paid, the existing receipt pipeline records the money as unallocated for operations to handle; the invoice is not paid twice. A provider-supported scheduled-charge cancellation should be added only after the exact API contract is confirmed for the merchant account.
