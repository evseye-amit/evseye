# Rider Wallet Phase 4: one-time Cashfree checkout

## Architecture

Phase 4 extends the existing `PaymentCollectionRequest` checkout order, `PaymentAttempt`, `PaymentProviderEvent`, `RiderPayment`, and `RiderPaymentAllocation` models. It does not introduce a second order or invoice model. The provider-neutral `PaymentProvider` interface supplies checkout order creation, payment status retrieval, and raw-body webhook verification. `CashfreePaymentProvider` implements those operations; the configured mock remains available for local tests.

The rider starts with `POST /rider-app/billing/invoices/:invoiceId/pay` and an `Idempotency-Key` header. `{ "useWallet": true }` is the default. The server authenticates the rider, checks invoice ownership, applies the Phase 3 wallet funding rules, and creates an external order only for the remaining outstanding amount. When the wallet covers the invoice, it returns `PAID` without a provider session. The `paymentSnapshot` records the invoice number, total, wallet contribution, and requested external amount; the current invoice remains the source of financial truth. The response contains the Cashfree `paymentSessionId` for future Flutter checkout. A client callback can only trigger server verification.

The existing order ID is a safe random `EVSEYE_PG_...` value. New checkout orders also receive a unique, readable `EVP-YYYYMMDD-...` payment number. An order is a request, not a receipt. The existing attempts and statuses track provider progress; a confirmed `RiderPayment` or wallet deposit transaction is created only after the server fetches a successful Cashfree payment for the order.

## Verification and accounting

The public `POST /webhooks/payments/cashfree/checkout` endpoint verifies the timestamp and signature against the **original raw body**, then stores an idempotent hashed event. It resolves the internal order from the provider order ID; no client ID in the payload is trusted. Both webhook and rider `POST /rider-app/billing/collections/:id/verify` fetch authoritative order payments from Cashfree. Amount, currency, order ID, and payment ID are checked before settlement. Provider-specific responses stay in the Cashfree adapter. Duplicate webhook delivery and a simultaneous status poll converge on the same collection and idempotency keys.

Each observed provider payment is recorded in `ProviderPaymentObservation` and as a `PaymentAttempt` under the collection. Mismatched amounts/currencies/orders and multiple provider successes remain visible for manual reconciliation, with no automatic invoice allocation. The checkout request receives a review failure code. Once a collection or provider attempt is `SUCCESS`, later stale failure or pending results cannot lower its status. The client reconciliation report includes reviewed provider observations and unallocated receipts.

For rental or onboarding invoices, verified payment uses the existing `RiderPaymentsService` receipt and invoice allocation in one serializable transaction. The amount is also posted through the wallet's immutable double-entry ledger between `CLEARING` and `PROVIDER_CLEARING`; this provider bucket is excluded from spendable wallet balance. If the invoice was paid by another path meanwhile, any external excess stays in `RiderPayment.unallocatedAmount` and is marked for review. The invoice is never overallocated.

For a Phase 3 security-deposit invoice, verified external money credits the `SECURITY_DEPOSIT` wallet bucket and creates `WalletInvoiceAllocation` rows with `EXTERNAL_RECORD` source. The deposit requirement and invoice are updated in the same transaction. Money that cannot be assigned to a deposit remains in provider clearing and is marked for review. The older agreement-level `RiderDeposit` checkout remains available for existing clients and is kept separate from the Phase 3 wallet deposit flow.

## Operations and boundaries

Riders can read `GET /rider-app/billing/collections` and `GET /rider-app/billing/collections/:id`; both enforce client and rider scope. Client administrators use the existing `/client/payment-reconciliation` report and retry verification endpoint. Order creation and webhook status changes produce existing audit records; raw secrets and full provider payloads are not stored in payment records. The Cashfree HTTP adapter selects sandbox or production centrally and does not automatically retry financial mutations after an uncertain transport failure.

Set `PAYMENT_PROVIDER=cashfree`, Cashfree client credentials, environment, API version, and checkout webhook URL through the existing configuration. The PG webhook uses the configured Cashfree **client secret** for timestamp plus raw-body HMAC verification, as required by [Cashfree's signature guide](https://www.cashfree.com/docs/payments/online/webhooks/signature-verification). Use Cashfree sandbox to exercise order creation, successful/failed/pending payment, duplicate webhook, invalid signature, and status polling. No live sandbox payment was made during implementation. Cashfree documentation confirms the [checkout API](https://www.cashfree.com/docs/api-reference/payments/latest/orders/create-order) used by this repository.

Wallet top-up is deferred because this phase's invoice and deposit paths do not require it. The existing mandate code is left as-is; this work adds no mandate or recurring-debit behavior. A future recurring flow can reuse the same provider verification and invoice accounting services. External refunds, bank settlement, disputes, and automated recovery remain outside this phase.

Known limits: Cashfree sandbox credentials were not available for a live provider transaction. The API stores the provider's order expiry time and marks a checkout expired when a provider status check reports `EXPIRED`; it does not schedule an automatic expiration job. A new checkout after a terminal failure uses a new collection with a new idempotency key, while attempts within one Cashfree order remain linked to its original collection. Provider-confirmed amount or currency mismatches are recorded for manual reconciliation rather than allocated automatically.
